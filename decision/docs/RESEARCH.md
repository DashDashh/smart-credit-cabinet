# Research: обоснование модели скоринга МСП

Документ описывает, **почему** модель скоринга устроена именно так: какие факторы, какие веса, какие источники, какие эксперименты. Нужен для защиты и для тех, кто будет развивать модель дальше.

## 1. Гипотеза

Ключевые факторы риска дефолта МСП:

1. **Кредитная история** (просрочки, использование кредитных линий) — главный фактор.
2. **Ликвидность** (способность покрыть краткосрочные обязательства) — второй.
3. **Долговая нагрузка** (доля платежей по кредитам в выручке).
4. **Рентабельность** (маржа, покрытие долга прибылью).
5. **Возраст и отрасль** — умеренное влияние.

Гипотеза проверяется на синтетике, сгенерированной по этим весам, и сравнивается с baseline (только `debt_load`).

## 2. Источники

| Источник | Что взято |
|---|---|
| **Roy & Shaw (2021), BWM+TOPSIS для МСП** | Веса факторов: кредитная история **12.82%**, ликвидность **8.75%**, срок погашения **7.69%**, рентабельность активов **6.35%**, финансовая гибкость **5.81%**. |
| **Dainelli et al. (2013), Basel rules для МСП** | Использование краткосрочных кредитных линий — **самый важный** фактор; капитализация **не влияет** на рейтинг; рентабельность продаж значима. |
| **Cheraghali & Molnár (2024), systematic review** | Доля дефолтов в реальных данных МСП — **5–15%**; дисбаланс классов — главная проблема; hold-out валидация обязательна. |
| **Saygılı et al. (2019)** | Финансовые и нефинансовые индикаторы компании (тип, штат, отрасль) значимо влияют на скор. |
| **Положение Банка России № 483-П** | Подход к оценке кредитного риска на основе внутренних рейтингов — общая методология. |
| **Михайличенко & Астафьева (2026)** | Российская специфика: классический скоринг плохо работает для микро-МСП; альтернативный скоринг (цифровой след) — next step. |

## 3. Как веса отражены в генераторе

Синтетика генерируется по латентной формуле `z` (см. `ml/generator.py`). Веса откалиброваны по литературе.

| Фактор | Вес в `generator.py` | Источник |
|---|---|---|
| `delinquencies_12m` | `+0.70 * delinq` + `+0.50 * (delinq >= 2)` | BWM+TOPSIS: кредитная история 12.82% |
| `credit_line_utilization` | `+0.30 * max(0, cu - 0.5)` | Dainelli et al.: ключевой фактор |
| `liquidity_ratio` | `-0.25 * (log_liq - log_med)` | BWM+TOPSIS: ликвидность 8.75% |
| `debt_service_coverage` | `-0.30 * (log_dsc - log_med)` | Dainelli et al.: рентабельность продаж |
| `loan_to_revenue` | `+1.8 * (ltr - 0.2)` | BWM+TOPSIS: срок погашения 7.69% |
| `term_months` | `+0.02 * max(0, term - 24)` | BWM+TOPSIS: срок погашения |
| `profit_margin_calc` | `-3.0 * pm` | Dainelli et al.: рентабельность |
| `age_months` | `-0.006 * (age - 36)` | Saygılı et al.: возраст значим |
| `company_type == "ip"` | `+0.10` | Saygılı et al.: тип компании |
| `industry` | `INDUSTRY_EFFECT[i]` | Saygılı et al.: отрасль |
| `business_status != active` | `+5.0` (hard stop) | — |
| `tax_arrears` | `+0.4` | — |

**Нелинейности** (для демонстрации ценности ML):

- `+1.5 * max(0, debt_load - 0.6)` — скачок риска после порога 0.6;
- `+0.8 * ((age < 12) & (debt_load > 0.4))` — интеракция «молодая компания + высокая нагрузка».

**Шум** `ε ~ Normal(0, 1.0)` — чтобы модель не выучила генератор наизусть. AUC ~0.87, а не 0.99.

## 4. Эксперимент: baseline vs full

**Baseline:** логистическая регрессия только на `debt_load` — самый сильный одиночный признак (корреляция +0.34 с `default`).

**Full:** логистическая регрессия на 23 признаках (18 числовых + 5 категориальных).

| Метрика | Baseline | Full | Δ |
|---|---|---|---|
| ROC-AUC | 0.692 | **0.873** | **+0.18** |
| PR-AUC | 0.339 | **0.614** | +0.28 |
| Brier | 0.207 | **0.071** | −0.14 |
| Precision (default) | 0.272 | **0.757** | +0.49 |
| Recall (default) | 0.446 | 0.410 | −0.04 |
| F1 (default) | 0.338 | **0.532** | +0.19 |

**Вывод:** мультифакторная модель оправдана — прирост ROC-AUC **+0.18**, PR-AUC **+0.28**, Brier **−0.14** (лучше калибровка). Baseline «видит» только один фактор и не различает «средних» клиентов.

**Почему recall чуть ниже:** `class_weight='balanced'` + калибровка сдвигают порог 0.5. В decision engine порог одобрения — **не 0.5**, а `score >= 65` (соответствует `p_default <= 0.35`). При этом пороге recall по дефолтам выше ~0.65. Precision/recall в `metrics.json` — для порога 0.5 (оценка качества модели), а не для бизнес-порога.

## 5. Почему логистическая регрессия, а не GBM

**Причины:**

1. **Объяснимость.** Коэффициенты `clf.coef_` дают прямой вклад в логит → `factors[]` в API. GBM требует SHAP, что сложнее и медленнее.
2. **Калибровка.** LogReg + `CalibratedClassifierCV` даёт честные вероятности (Brier 0.071). GBM без калибровки часто «переуверен».
3. **Скорость.** LogReg обучается за секунды, инференс — миллисекунды. Для хакатона это важно.
4. **Соответствие литературе.** В банках для скоринга МСП часто используют scorecard / LogReg (BWM+TOPSIS, Basel rules), а не GBM — из-за регуляторных требований к объяснимости.

**Next step:** GBM (LightGBM) как **эксперимент** — если покажет +0.05 ROC-AUC, можно использовать **ансамбль** (LogReg для объяснимости + GBM для точности). Но в MVP — LogReg.

## 6. Fallback: зачем и как

**Зачем:** если ML недоступна (`model.pkl` не загрузился, контейнер упал, таймаут) — сервис **не должен падать**. Fallback — детерминированная scorecard с экспертными весами.

**Как:** `app/fallback.py` — балльная модель. Те же признаки, что ML, но с **экспертными весами** (из литературы) и **симметричными бонусами/штрафами** (бонус за хорошие значения, штраф за плохие).

**Калибровка:** Spearman между `fallback_score` и `ml_score` на 20 000 строках — **0.852**. Это значит, что fallback **согласован** с ML по ранжированию: «хорошие» клиенты получают высокий score, «плохие» — низкий.

**Разрыв средних:** fallback mean ~54, ML mean ~88 (разрыв ~34). Это **осознанно**: fallback консервативнее ML. При деградации ML банк должен быть осторожнее, а не наоборот. В next step — сдвинуть пороги для fallback на −5, чтобы компенсировать.

**Ограничения fallback:**

- Не учитывает нелинейности (порог `debt_load > 0.6`, интеракция `age < 12 & debt_load > 0.4`).
- Не учитывает `credit_line_utilization` в полной мере (только линейно).
- Не калиброван так же хорошо, как ML (Brier выше).

Но fallback **детерминирован**, **объясним** и **не падает** — это его главная ценность.

## 7. Data check vs scoring

**Проблема:** в первой версии `needs_info` был порогом score (30–45). Это смешивало «средний риск» и «неполные данные»:

- клиент с полными данными и средним риском → `needs_info` (хотя должен получить `approved_with_conditions` или `rejected`);
- клиент с неполными данными → `scoring.predict` вызывался на мусоре, fallback возвращал дефолтный score.

**Решение (Вариант B):** `needs_info` — **результат `check_data_completeness`**, а не порог score. Если данных не хватает — ML **не вызывается**, `model_version = "data-check-v1"`, `score = 0.0`.

**Next step (Вариант A):** вынести `DataCheckResult` в отдельное поле контракта:

```python
class DataCheckResult(BaseModel):
    status: Literal["complete", "incomplete", "invalid"]
    missing_fields: list[str]
    reasons: list[Factor]

class DecisionResponse(BaseModel):
    score: Optional[float]      # None, если скоринг не запускался
    decision: Optional[DecisionType]
    data_check: DataCheckResult
    ...
```


## 8. Российская специфика

- **Классический скоринг на бухотчётности плохо работает для микро-МСП** (Михайличенко & Астафьева, 2026): нет длительной кредитной истории, отчётность «серая».
- **Альтернативный скоринг** (цифровой след, обороты по счёту, данные маркетплейсов) — next step. В MVP не используется (нет данных), но заложен в архитектуру: `DecisionRequest` можно расширить полем `alternative_data`.
- **Доля просрочки в портфеле МСП растёт** (с 4.4% до 5% к концу 2025) — модель должна быть **консервативной**. Порог 65 (а не 60) — осознанно консервативный.

## 9. Ограничения

- **Синтетика**, не реальные данные. Веса откалиброваны по литературе, но не проверены на реальных заявках.
- **Не используются** цифровой след, обороты по счёту, данные маркетплейсов (next step).
- **Продуктовые лимиты** — в коде, не в БД. В next step — `products.yaml`.
- **`manual_review`** не реализован (это состояние Java).
- **LLM для документов** не в MVP (next step — гибрид: парсер + LLM как fallback).
- **GBM** не используется (next step — эксперимент, возможно ансамбль).

## 10. Next steps

1. **GBM (LightGBM)** — проверить, даёт ли +0.05 ROC-AUC. Если да — ансамбль (LogReg для объяснимости + GBM для точности).

3. **`products.yaml`** — вынести продуктовые лимиты из кода, общий с Java.
4. **Альтернативный скоринг** — цифровой след, обороты по счёту.
5. **LLM для документов** — гибрид: парсер + LLM как fallback.
6. **Калибровка fallback** — сдвинуть пороги на −5, чтобы компенсировать консервативность.
7. **Реальные данные** — проверить модель на исторических заявках (если появятся).
8. **Мониторинг** — drift detection, переобучение раз в квартал.
